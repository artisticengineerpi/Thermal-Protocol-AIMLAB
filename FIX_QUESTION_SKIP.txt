Issue: Question screen sometimes skipped, jumping directly to next trial
Status: ✓ FIXED

================================================================================
PROBLEM DESCRIPTION
================================================================================

Symptom:
  • Most trials work correctly
  • Sometimes question screen appears briefly then skips to next fixation
  • Appears to "auto-answer" without participant input
  • Happens intermittently (not every trial)

Root Cause:
  1. Participant accidentally presses key during stimulation phase
  2. Browser captures keypress and sends to server
  3. Keypress stored in browser's last_keypress buffer
  4. When show_question() starts, it immediately reads stale keypress
  5. Question "answered" instantly, skips to next trial

Why It's Intermittent:
  • Only happens if participant touches keyboard during stimulation
  • Buffer not cleared between phases
  • No minimum wait time to validate responses

================================================================================
THE FIX
================================================================================

Applied 4-layer protection against stale keypresses:

╔══════════════════════════════════════════════════════════════════════════╗
║ Layer 1: Buffer Clearing (Before Showing Question)                      ║
╚══════════════════════════════════════════════════════════════════════════╝

Clear ALL pending inputs before displaying question:

    # Clear browser keypress buffer
    self.browser_display.get_keypress()  # Discard stale
    self.browser_display.get_keypress()  # Double clear
    
    # Clear keyboard event buffer
    timeout_time = time.time() + 0.05
    while time.time() < timeout_time:
        keyboard.read_event(suppress=False, timeout=0.01)

Result: Any accidental keypresses from stimulation phase are discarded

╔══════════════════════════════════════════════════════════════════════════╗
║ Layer 2: Settling Delay                                                 ║
╚══════════════════════════════════════════════════════════════════════════╝

Wait 200ms after clearing buffers:

    time.sleep(0.2)  # Let system settle

Result: Prevents immediate response registration

╔══════════════════════════════════════════════════════════════════════════╗
║ Layer 3: Final Buffer Clear                                             ║
╚══════════════════════════════════════════════════════════════════════════╝

Clear one more time right before listening:

    if self.browser_display:
        self.browser_display.get_keypress()

Result: Extra safety against any new stale input

╔══════════════════════════════════════════════════════════════════════════╗
║ Layer 4: Minimum Wait Time (300ms)                                      ║
╚══════════════════════════════════════════════════════════════════════════╝

Ignore responses that come too fast:

    min_wait_time = 0.3  # 300ms minimum
    start_time = time.time()
    
    # In response loop:
    if elapsed >= min_wait_time:
        # Accept response
    else:
        # Ignore and log as "too fast"

Result: Any response < 300ms is rejected as likely stale

╔══════════════════════════════════════════════════════════════════════════╗
║ Bonus: Debouncing on Keyboard Input                                     ║
╚══════════════════════════════════════════════════════════════════════════╝

Prevent double-registration from held keys:

    if keyboard.is_pressed('1'): 
        time.sleep(0.1)  # Debounce delay
        return '5'

Result: Held keys don't trigger multiple times

================================================================================
TECHNICAL DETAILS
================================================================================

Buffer Clearing Strategy:
  • Browser: Call get_keypress() multiple times (consumes buffer)
  • Keyboard: Loop read_event() until no more events (50ms timeout)
  • Settling: 200ms delay lets all systems stabilize
  • Final: One more clear right before listening

Minimum Wait Time:
  • 300ms threshold (configurable)
  • Prevents responses faster than human reaction
  • Typical human reaction: 200-300ms minimum
  • Adds safety margin

Response Validation:
  if elapsed >= min_wait_time:
      ✓ Accept response
  else:
      ✗ Reject and log warning
